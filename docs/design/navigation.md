# Navigation and routes

The menu and URL structure group every page by **workspace**, the part of the hospital where the
work happens, and then by **section**, the job being done there. The grouping takes its cue from
the module-based menu of established hospital systems, reviewed from a recorded Unumed demo (see
[Reference inventory](#reference-inventory)). The names, routes and behaviour are MedSafe's own.

The single source of truth is `WORKSPACES` in `apps/manager/navigation.py`. The menu, the
breadcrumbs, the post-sign-in redirect and the tests all read it. The route tables below are
generated from it, so regenerate them when it changes (see [Changing the menu](#changing-the-menu)).

## Principles

- **One place for every page.** Each page belongs to exactly one workspace and section. A page with
  several tabs gets one menu entry per tab, linked with `?tab=`, so the menu doubles as a table of
  contents.
- **Routes follow the menu.** A page's path starts with its workspace (`/outpatient/`,
  `/laboratory/`, `/diagnostics/`, `/procedures/`, `/pharmacy/`, `/inventory/`, `/accounting/`,
  `/admin/`). Detail pages sit under their list page, for example `/accounting/invoices/42/`.
- **Show the roadmap, never a dead end.** Pages that are not built yet appear greyed out with a
  *Planned* tag and are not links. Each one has a reserved route, and a test makes sure that route
  is still free.
- **Access decides visibility.** A user sees a workspace only if they hold a module that owns one
  of its pages, live or planned. Planned pages follow the module that will own them.
- **Old links keep working.** Every path that changed redirects permanently (301), query string
  included.

## Behaviour

| Element | Behaviour |
| --- | --- |
| Workspaces | Fold open and closed (`<details>`). The one holding the current page is open; others the user opens stay open across pages (stored in `localStorage`). |
| Current page | The live page whose path is the longest prefix of the URL, preferring a matching `?tab=`. Detail pages highlight their list page. |
| Tabs | Choosing a menu entry for another tab of the open page switches tab without a reload. Switching tab on the page moves the highlight and the breadcrumb with it. |
| Find a page | Filters pages by page, section or workspace name. `/` focuses it from anywhere outside a form field, **Enter** opens the first live match, and **Esc** clears it. |
| Show planned pages | A toggle at the foot of the menu, remembered per browser. It is applied before the first paint, so hidden pages never flash. |
| Breadcrumb | Workspace / Section / Page in the top bar. On a detail page the last crumb is the page's own title. |
| Narrow screens (below 64rem) | The menu becomes a drawer opened from the top-bar button or `/`. A backdrop click or **Esc** closes it and returns focus to the button. |
| Motion | Only the drawer (260 ms in, 180 ms out) and the 150 ms workspace chevron move. Hover colour changes take 120 ms and apply only on devices that can hover. Reduced-motion users get no movement. |

## Changing the menu

1. Edit `WORKSPACES` in `apps/manager/navigation.py`. Use `live(label, url_name, *modules, tab=...)`
   for a built page and `planned(label, route, *modules)` for a reserved one.
2. When a planned page is built, register its route and change its entry from `planned` to `live`.
3. When a route moves, add a `moved()` redirect in `core/urls.py`.
4. Run `python manage.py test apps.manager`. `NavigationDefinitionTest` opens every live entry,
   checks that its tab exists, and checks that no planned route is already taken.
5. Regenerate the route map above with `python manage.py navigation_routes` and paste its output
   over the per-workspace tables.
